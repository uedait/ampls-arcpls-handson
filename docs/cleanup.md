# 後片付け・切り戻し

[README](../README.md) / [事前確認](prerequisites.md)

## 原則

後片付けを実施する前に、削除対象の完全なリソース ID、所有者、残すリソース、ログの保管期間、影響を提示し、構築時とは別に削除の承認を取得してください。

削除対象は今回作成し、削除を承認されたリソースに限定してください。既存 DNS、Firewall、VNet、Resolver、VM、LAW / AMPLS の削除は、業務通信や監視を停止させるリスクがあるため、実施しないでください。RG 内に既存リソースが含まれる場合は、今回の対象を個別に削除します。

## 1. 試験中に問題が起きた場合

1. 試験を止め、ネットワーク / DNS / 監視の担当者に対象と時刻を連絡します。
2. Proxy の一時解除試験中なら、記録した Arc の `proxy.url` / `proxy.bypass` を復元し、チェックが成功することを確認します。
3. 今回変更した通信規則を、承認された復元値へ戻します。ラボの構築用インターネット接続へ戻す必要がある場合は、3台すべてに公開送信を再許可する影響を確認し、承認後に下記の Build 切替を実行してください。②③の収集検証へ戻る前には Restricted に切り替えて再確認します。
4. DNS の変更が原因なら、今回**新規作成した**条件付きフォワーダーだけを削除します。既存の転送先を承認の上で変更した場合は、元の転送先、タイムアウト、AD 複製範囲を復元します。
5. 作業前後の DNS 応答と既存業務の疎通を担当者が確認します。必要なキャッシュ更新は対象クライアントとレコードを担当者が確認して行ってください。共有 DNS サーバー全体の不用意な再起動は業務の名前解決を中断するリスクがあるため、実施しないでください。
6. AMPLS / DNS zone の変更で既存監視に影響した場合は、変更記録に従い今回の link / record / mode を復元してください。既存の関連付けは作業前の記録と照合して維持します。

問題を解消できなければ、既存業務の復旧を優先してハンズオンを中断します。

```powershell
.\infra\lab\Set-LabInternetAccess.ps1 `
  -ExpectedTenantId '<Tenant ID>' `
  -ExpectedSubscriptionId '<Subscription ID>' `
  -ResourceGroup '<ラボ専用 RG>' `
  -Prefix arclab -Mode Build
```

切替スクリプトが途中で失敗した場合は、変更済みと表示された NSG と残りの NSG の access を個別に照合してください。復元は実際の規則の状態と通信確認で判定します。

## 2. 検証対象の収集設定を外す

1. 検証結果を安全な保管先に保存し、LAW のデータを残すか削除するか決めてください。LAW の削除はデータの喪失につながるため、保管対象を退避してから削除を承認します。
2. Portal の今回の DCR から、今回追加した Azure VM / Arc machine の関連付けを外します。元から存在する関連付けは作業前の記録と照合して維持してください。
3. DCE の「リソース」から今回の設定取得先の関連付けを外します。作業前から DCE があった対象は、事前記録に従い元へ復元します。
4. 今回だけの AMA で、ほかの DCR / 管理機能が使っていないことを確認できた場合に限り、対象の「拡張機能」から `AzureMonitorWindowsAgent` を削除します。
5. Azure VM のマネージド ID の利用先を確認し、アプリケーション等で使用中の ID は有効な状態を維持してください。

## 3. 今回の Arc 登録を解除する

1. AMA 等の拡張機能を除去してよいか確認します。Arc の解除は管理機能、ポリシー、ESU 等に影響するため、今回登録した machine を対象として担当者の承認を取得してください。
2. 対象サーバーで、正しいテナントと machine であることを `azcmagent show` で確認します。
3. 必要な Entra ID / ARM の Proxy 到達性を残したまま、公式の[Arc Agent 管理手順](https://learn.microsoft.com/azure/azure-arc/servers/manage-agent)に従い `azcmagent disconnect` で今回の登録を解除します。手動認証の案内に従い、作業記録には解除対象と結果を記載してください。
4. Portal で対象の Arc machine と PLS 関連付けの解除を確認します。登録解除に失敗した場合は、Azure 側とサーバー側それぞれの状態を調査して復旧してください。
5. 今回導入した Agent を残す必要がなければ「アプリと機能」から Azure Connected Machine Agent をアンインストールします。手順と再起動要否を確認します。
6. 検証用の Event Source `AmplsArcHandson` を取り除く場合は、他用途で使っていないことを確認して `Remove-EventLog -Source AmplsArcHandson` を使用します。Application ログ全体の削除は他アプリケーションの監査記録も失うリスクがあるため、実施しないでください。

## 4. Azure 側の検証リソースを削除する

Portal で対象 ID と依存関係を確認して、個別に実施します。

1. 今回だけの DCR を削除します。
2. AMPLS から、今回追加した LAW / DCE の scoped resource 関連付けを外します。共有 scope を残す場合、ほかの関連付けは維持します。
3. 今回だけの AMPLS PE / Arc PE を削除し、DNS zone group とレコードへの影響を確認します。
4. 関連 machine が残っていない今回だけの Arc PLS、参照先を外した今回だけの AMPLS を削除します。
5. 他で使っていない今回の DCE / LAW を削除します。LAW を残す場合は、不要な診断ログ送信設定と課金対象も確認します。
6. 今回作成し、他の PE / VNet が使っていない zone / VNet link / レコードのみを削除します。Windows DNS の条件付きフォワーダーも、残す閉域サービスがないか確認して戻します。
7. 今回だけの Firewall 診断設定、Application rule、Explicit Proxy の変更を戻します。共有 Policy 全体の削除・無効化は業務通信を停止させるリスクがあるため、実施しないでください。

LAW / DCE は、AMPLS の scoped resource 関連付けを解除してから削除してください。削除エラーが出た場合は対象 ID と依存関係を調べ、担当者と対応を決めます。

## 5. 任意ラボの終了

①で作った専用 RG の全リソースを棚卸しし、②③の残存リソースと所有者も確認します。専用であることと一括削除の承認が確認できた場合のみ、Portal からその RG を削除します。個別削除する場合は、VM 内の後片付けと必要なファイルの回収を済ませてから Bastion とその専用 Public IP を削除してください。VM 用3個を含む計5個の Public IP、3個の NIC NSG、ディスク、Firewall、Resolver、PE 等の残存も確認します。

L1 内の L2 を片付ける場合は、対象 VM と使用中の差分・親 VHDX の対応を確認して削除承認を取得してください。承認した L2 の VM と差分ディスクを先に削除し、ほかの差分ディスクが参照していない親ディスクを後で削除します。参照中の親ディスクの削除・変更・移動は L2 の起動を失敗させるリスクがあるため、実施しないでください。初回セットアップに失敗した場合は、資格情報を含む応答ファイルが残ったディスクも保護対象として確認します。

VM 停止後も Bastion / Firewall / Resolver / Public IP / ディスク等の課金は続くため、予算期限内に削除が完了したか担当者が確認してください。既存業務リソースを含む RG の一括削除は、業務環境を失うリスクがあるため、実施しないでください。
